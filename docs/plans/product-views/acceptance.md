# Acceptance journeys in the native plugin

The clickdummy supplies working examples. A journey passes when visible plugin controls, durable Vault files and host adapters agree after reload. The coordinator owns this matrix. Each implementer owns the earliest failing assertions for the part their packet delivers.

## Fixtures

- **Blank product** — a disposable Vault with no product notes, no assumed user and AI disabled. Add a second project with overlapping short record IDs to test isolation.
- **Existing product** — a project modeled on Kundenportal with a job, vision, research, PRD requirement, two planning contexts, two stories sharing a PBI, an unrelated sibling, inherited NFRs and a one-hop domain neighbor. Include an existing Base/Markdown backlog with mapped fields, an external edit and unknown frontmatter.
- **Delivery history** — a temporary real Git repository with two note commits and another independently changed file. Supply attributable run, attempt, PR, commit and CI records. Include a frozen and a follow-up revision, a legacy package with missing fields and a captured empty scope. Label fixture and live-service evidence separately.
- **Agent** — a controllable provider adapter that records calls and can delay, fail, emit malformed content or complete after cancellation. Use the native provider path for a separate authorized live smoke check where available. Keep accounts and credentials out of test fixtures.

## Verification and release evidence

1. **Each behavior.** Use TDD's Red–Green–Refactor cycle. Write a focused native test, observe the intended failing assertion, implement the smallest passing change, and refactor where useful with the tests green. Apply the same cycle to behavioral defects found during review. For Vitest use `npm test -- <actual-test-path>`. Record the test name, command, red assertion and green result. For a disputed reference behavior, run `python -m unittest discover -s docs/concept/tests` with the prerequisites in the [concept guide](../../concept/README.md). Those tests target the standalone HTML.
2. **Each packet.** A fresh independent reviewer opens the clickdummy route and integrated native view with equivalent fixtures, exercises the primary action, navigates back and reloads. Inspect focus, empty/error states and a narrow leaf. For dense views also inspect a wide/collapsed-sidebar layout and both host themes. Check that dialog actions remain reachable on short screens, Escape returns focus, drag has a keyboard equivalent and disclosure preserves selection. Record evidence for every due criterion and recheck findings on the corrected revision. Before PASS, the reviewer saves and links the normal and narrow [side-by-side comparisons](orchestration.md#capture-the-comparison-pair) in the ledger and opens both links. The next packet requires those images, independent PASS and `npm run verify` exit 0 on the same integrated revision.
3. **At each checkpoint.** Run newly eligible journeys and those affected by changed contracts. Exercise real host reload, split/popout navigation and an outside Vault edit. Record fixture names, commands and outcomes. Distinguish real Git and live provider/Factory evidence from a host check backed by a fixture.
4. **Before the V24 commit.** Inspect the delivered `package.json` and `scripts/verify.mjs`. Run `npm run verify:full` and the native `npm run test:e2e` separately if the former omits the latter. Run the journeys with the installed plugin in a disposable Vault. Check unload, offline startup with AI off, both theme and localization catalogs, and working copy preservation. Record exit codes, environment and any outstanding external verification in the [ledger](progress.md).

For every packet, the coordinator follows the [per-view Git checkpoint](orchestration.md#commit-the-accepted-view) after verification and independent PASS. Confirm that the commit contains the reviewed changes, tests, both PNGs and signed ledger entry before moving on.
